# 免费额度测算、监控与故障排查

整套系统的容量按 **Cloudflare Workers + D1 免费额度** 设计，监控直接看 Cloudflare 控制台和自带日志，不额外把监控指标写回 D1。

---

## 1. 免费额度够不够用

Cloudflare Workers Free 的日常基线如下：

- **Worker 请求数**：100,000 次/天（静态页面和 `/dl/*` 安装包不计入）
- **Worker CPU 时间**：10 ms/次
- **D1 写入 / 读取**：100,000 行写/天、5,000,000 行读/天
- **D1 存储**：单库 500 MB（账户 5 GB）

### 实际消耗测算

按默认 **心跳 300 秒（5 分钟）、流量上报 900 秒（15 分钟）** 计算：

- **请求数**：每台节点每天约 `288` 次请求；哪怕跑满 **100 台节点**，每天也只占免费请求额度的 **29%**。
- **D1 写入行数**：

| 规模 | 心跳写 | 报表凭证 | 各类小时桶 | 周期汇总 | 每日总写入 | 占免费额度 |
| --- | --- | --- | --- | --- | --- | --- |
| 20 节点 / 50 组合 / 50 用户 | 5,760 | 1,920 | 6,816 | 4,800 | **19,296** | **19.3%** |
| 100 节点 / 100 组合 / 50 用户 | 28,800 | 9,600 | 19,296 | 4,800 | **62,496** | **62.5%** |

> **关键省钱开关**：流量上报间隔（默认 900 秒）最影响 D1 写入量；每 15 分钟的周期扫描任务在无状态变更时几乎不写库。可用 `npm run capacity` 在本地压测并核对读写行数和 p95 CPU 耗时（目标管理与订阅接口 p95 ≤ 5 ms）。

## 2. 日志与日常关注项

- **Worker 日志**：每条请求带 `request_id`、路由、状态码、错误码、耗时和 D1 读写行数（已过滤 Token、UUID 和请求体）。
- **Agent 日志**：通过 `journalctl -u zako-agent -f` 查看，记录 `report_id`、当前配置版本、用户版本和重试情况。
- **建议关注的异常信号**：
  - D1 日写入或 Worker 请求接近 80% 配额
  - 节点连续 3 个心跳周期未上报（面板显示 `offline`）
  - 节点上报配置校验失败或自动回滚
  - 定时任务执行报错

## 3. 常见故障系统会怎么自愈

| 出了什么事 | 系统会怎么处理 | 你需要做什么 |
| --- | --- | --- |
| **Worker 或 D1 临时挂了** | Agent 把待发流量存在本地 BoltDB 并指数退避重试；订阅接口返回 `503` | 等恢复即可，恢复后本地积压报表会自动补报 |
| **Worker 免费额度打满了** | Cloudflare 边缘返回 `429` / `1027`，Agent 按 `Retry-After` 等待，本地不丢数据 | 调大心跳/上报间隔，或升级付费计划 |
| **单台节点断网或 Agent 挂了** | 正在连的代理流量不受影响；超过 3 个心跳周期后面板标为 `offline`，新订阅不再下发它 | 登录节点看 `systemctl status zako-agent` 和网络连通性 |
| **Xray 统计接口异常** | 节点标为 `degraded`，但**依然保留在订阅里**（代理还能用）；流量报表带 `has_counter_gap` | 检查节点上 Xray 的 `127.0.0.1:10085` 监听与 `journalctl -u xray` |
| **Xray 意外重启（计数器清零）** | Agent 发现读数变小，自动把当前读数直接当增量并标断层，不会扣出负数流量 | 无需手工修账 |
| **下发的新配置语法错了** | Agent 跑 `xray run -test` 失败后直接中止，旧 Xray 继续跑，同时把报错传回面板 | 在面板查看节点配置版本的错误信息，改好后重发 |
| **新配置重启后健康检查失败** | Agent 自动还原备份的旧配置并重启 Xray，向面板报 `failed` | 同上，排查端口冲突或路由规则错误 |
| **节点上 `state.db` 丢了** | 重连面板后自动重新拉取用户和配置；丢掉的那小段基线通过断层机制平滑接上 | 无需人工干预，下个周期恢复正常 |
